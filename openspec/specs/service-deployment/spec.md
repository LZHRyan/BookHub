# service-deployment Specification

## Purpose
定义 BookHub 的部署与运维行为契约：单镜像即可运行、配置全部来自环境变量、启动顺序与健康探针语义、数据持久化与备份恢复、升级与子路径反代适配，以及结构化日志输出。

## Requirements

### Requirement: 镜像 MUST 自包含并以非 root 运行

发布产出的容器镜像 MUST 自带运行所需的全部依赖与静态资源，单个容器 MUST 即可提供完整功能，启动 MUST NOT 依赖外部数据库、缓存、对象存储或外部网络服务。容器内进程 MUST 以非 root 身份运行；运行期需要的可写数据目录 MUST 对该用户可写，其余应用文件 MUST 对该用户只读。

#### Scenario: 只提供一个数据卷即可完整运行

- **WHEN** 部署者以最小配置启动该镜像，仅挂载一个数据卷
- **THEN** 站点、管理端与对外接口都可正常使用
- **AND** 无需额外安装或连接任何外部服务

#### Scenario: 进程以非 root 身份运行

- **WHEN** 容器启动并开始对外服务
- **THEN** 运行服务的进程用户标识不是 root
- **AND** 该进程对数据目录具备读写权限

### Requirement: 配置 MUST 全部来自环境变量

所有运行配置 MUST 通过环境变量提供，且 MUST 随仓库提供一份覆盖全部配置项、默认值与说明的示例清单。缺少必需配置时进程 MUST 启动失败，并以明确的错误信息指出缺失的配置项；MUST NOT 使用不安全的内置默认值静默启动。

其中与安全直接相关的两项 MUST 可配置且默认取安全值：

- `TRUSTED_PROXIES`：可信反向代理的 IP/CIDR 列表，非法条目 MUST 让启动失败；默认为空，表示**不采信任何** `X-Forwarded-For` / `X-Real-IP`，客户端 IP 取直连 peer。
- `MAX_UPLOAD_FILES`：单次批量上传的文件个数上限，默认 50。

#### Scenario: 缺少必需配置时启动失败并指名

- **WHEN** 部署者未提供会话签名密钥等必需配置就启动容器
- **THEN** 容器以非零退出码退出
- **AND** 日志明确指出缺少哪一项配置，且服务未对外监听

#### Scenario: 未提供的可选配置使用默认值

- **WHEN** 部署者只提供必需配置，未设置可选配置项
- **THEN** 服务使用文档中声明的默认值正常启动
- **AND** 启动日志可看出各配置项的实际生效值（敏感值除外）

#### Scenario: 未配置可信代理时不采信转发头

- **WHEN** 部署未设置 `TRUSTED_PROXIES`，请求携带伪造的 `X-Forwarded-For`
- **THEN** 限流与审计使用直连地址，伪造头被忽略
- **AND** 伪造不同取值不会换来新的限流额度

#### Scenario: 配了可信代理才采信转发头

- **WHEN** `TRUSTED_PROXIES` 包含反向代理所在网段，且直连 peer 落在该网段
- **THEN** `X-Forwarded-For` 的第一跳被用作客户端 IP
- **AND** 不在该网段的直连请求即使带该头也仍取直连地址

#### Scenario: 非法的可信代理条目让启动失败

- **WHEN** `TRUSTED_PROXIES` 中出现不是合法 IP 或 CIDR 的条目
- **THEN** 配置解析失败并给出明确的配置错误信息
- **AND** 服务不启动

### Requirement: 启动 MUST 按固定顺序准备数据

容器启动 MUST 依次完成：确认数据目录可写、执行数据库迁移、幂等确保初始管理员存在、再启动对外服务。任一前置步骤失败时 MUST NOT 启动对外服务，并以非零退出码退出且错误信息指出失败阶段。迁移 MUST 幂等，重复启动 MUST NOT 重复施加已应用的变更或破坏既有数据。

#### Scenario: 迁移失败时不对外提供服务

- **WHEN** 启动过程中数据库迁移失败
- **THEN** 容器以非零退出码结束
- **AND** 对外端口上没有可接受请求的服务

#### Scenario: 重复启动保持幂等

- **WHEN** 同一数据卷上的容器被重启多次
- **THEN** 已应用的迁移不重复执行，初始管理员不被重复创建或改密
- **AND** 既有内容与账号保持原样

### Requirement: 健康探针 MUST 区分存活与就绪

`/healthz` MUST 表示进程存活：只要服务能响应请求即返回 200，MUST NOT 因数据存储问题而失败。`/readyz` MUST 表示可对外服务：其中包含对数据存储可读且可写的探测，探测不通过时 MUST 返回非 2xx 状态码。两者 MUST 无需鉴权即可访问。

#### Scenario: 正常运行时两者均通过

- **WHEN** 服务已就绪且数据存储可用
- **THEN** `/healthz` 与 `/readyz` 都返回 2xx
- **AND** 容器编排可据此判定实例可接收流量

#### Scenario: 数据不可写时仅就绪失败

- **WHEN** 数据存储变为只读或不可写
- **THEN** `/readyz` 返回非 2xx
- **AND** `/healthz` 仍返回 2xx，表示进程本身存活

### Requirement: 数据 MUST 持久化在挂载卷上

数据库与运行期产生的全部数据 MUST 位于同一个可挂载的持久目录，MUST NOT 依赖容器可写层的任何状态。容器重启、重建与镜像升级后，内容、版本历史、账号与站点配置 MUST 保持不变。

#### Scenario: 重启后数据不丢失

- **WHEN** 容器被停止并重新启动，仍挂载同一数据卷
- **THEN** 此前创建的 Book、章节正文与历史版本都可原样读取
- **AND** 管理员账号与站点配置保持不变

#### Scenario: 用新容器替换旧容器后数据一致

- **WHEN** 删除旧容器并用新容器挂载同一数据卷启动
- **THEN** 对外接口与页面返回的内容与替换前一致
- **AND** 不出现需要重新初始化或重新创建账号的情况

### Requirement: 备份 MUST 可在运行中产出并可恢复

运维 MUST 能通过随镜像提供的方式产出数据卷的一致备份，备份 MUST 可在服务运行期间执行而不产生损坏或不一致的副本；用该备份在空数据卷上恢复后，MUST 得到内容、历史版本与账号均可读的实例。恢复操作 MUST 在服务停止时执行，并在恢复完成后服务能正常启动。

#### Scenario: 运行中备份得到一致副本

- **WHEN** 服务正常对外提供内容时执行备份
- **THEN** 备份过程不中断的内容读取请求
- **AND** 备份产物包含数据库与内容数据，可用于后续恢复

#### Scenario: 用备份恢复出可用实例

- **WHEN** 在空数据卷上用一份备份执行恢复并启动服务
- **THEN** 站点可正常访问，章节正文与历史版本与备份时刻一致
- **AND** 既有管理员账号可继续登录

### Requirement: 升级 MUST 保持既有数据可用

升级 MUST 通过替换镜像并重启完成，启动过程中自动执行数据迁移，既有数据在新版本下 MUST 可读可写。迁移 MUST 遵循只增不删的原则，使得回退到旧版镜像后旧版本仍能读取该数据；回退流程 MUST 为停止服务、恢复备份、启动旧版镜像。

#### Scenario: 升级后旧数据可读

- **WHEN** 用新版本镜像在同一数据卷上启动服务
- **THEN** 升级前创建的 Book、章节与版本历史都能正常读取
- **AND** 对外接口的既有路径继续按原契约返回

#### Scenario: 回退到旧版本可用

- **WHEN** 运维停止服务、恢复升级前的备份并启动旧版镜像
- **THEN** 服务正常启动并返回备份时刻的内容
- **AND** 不因数据库结构变更而启动失败

### Requirement: 子路径部署 MUST 通过 ROOT_PATH 正确生成链接

当服务部署在反向代理的子路径下时，通过 `ROOT_PATH` 声明该前缀后，页面链接、重定向、静态资源地址与接口文档地址 MUST 都带上该前缀；页面与响应 MUST NOT 生成指向站点根路径的绝对链接。未设置 `ROOT_PATH` 时行为 MUST 与根路径部署一致。

#### Scenario: 子路径下链接与静态资源带前缀

- **WHEN** 服务以 `ROOT_PATH=/kb` 部署并经反向代理访问 `/kb/`
- **THEN** 页面中的导航链接、静态资源地址与重定向都指向 `/kb/...`
- **AND** 静态资源可正常加载，不出现 404

#### Scenario: 未设置前缀时按根路径工作

- **WHEN** 部署未设置 `ROOT_PATH`
- **THEN** 所有链接与静态资源地址指向站点根路径
- **AND** 与子路径部署返回相同的页面内容结构

### Requirement: 日志 MUST 结构化输出到标准流

运行日志 MUST 输出到标准输出或标准错误，MUST NOT 依赖写入容器内文件。每条日志 MUST 为结构化格式，至少包含时间戳、级别与事件名；与请求相关的日志 MUST 包含请求标识与来源 IP。日志 MUST NOT 记录密码、会话令牌或完整鉴权凭据。

#### Scenario: 标准流中可读到结构化日志

- **WHEN** 服务处理若干请求后查看容器标准输出
- **THEN** 每行日志都是可解析的结构化记录，含时间戳、级别、事件名
- **AND** 请求相关日志带请求标识与来源 IP

#### Scenario: 敏感信息不进入日志

- **WHEN** 管理员登录、修改密码或使用 API 凭据发起请求
- **THEN** 日志中不出现明文密码、会话令牌或完整凭据值
- **AND** 仍可通过请求标识定位该次请求的处理过程

### Requirement: Webhook MUST 通过管理 API 管理

管理 API MUST 提供 Webhook 的列表、创建、删除、测试投递、以及失败投递的重试端点。创建 MUST 返回一次性密钥；删除 MUST 为停用（保留历史投递记录）。全部操作 MUST 复用 `admin` 作用域与审计约定。

#### Scenario: 创建与列表

- **WHEN** 使用 `admin` 作用域创建 Webhook
- **THEN** 返回 201，含 id、`secret`（仅此一次）与订阅的事件
- **AND** 列表返回的项不含 `secret`

#### Scenario: 测试投递

- **WHEN** 调用某 Webhook 的测试端点
- **THEN** 立即向该地址发送一条 `webhook.test` 事件
- **AND** 响应里返回该次投递的状态码或错误

#### Scenario: 重试失败投递

- **WHEN** 调用某条投递记录的重试端点
- **THEN** 重新发送同一请求体并更新记录
- **AND** 返回新的状态码与尝试次数

### Requirement: CI MUST 校验 lint、测试与镜像构建

仓库 MUST 提供持续集成工作流：安装依赖后执行 `ruff check`、`pytest`，并构建 Docker 镜像。任一步失败 MUST 让工作流失败。工作流 MUST 不需要任何密钥即可跑通（测试使用临时 SQLite 与内存数据）。

#### Scenario: 推送触发校验

- **WHEN** 向仓库推送提交
- **THEN** CI 依次执行 lint、测试与镜像构建
- **AND** 测试使用仓库内的 `.venv` 之外的干净环境安装依赖

### Requirement: 启动 MUST 准备内置指南（可关闭）

启动流程在数据库迁移与初始管理员就绪之后 MUST 幂等准备内置《AI Agent 接入使用指南》。失败 MUST NOT 阻止服务对外提供（与其它启动准备项一致：记日志、继续启动）。`BUILTIN_GUIDE_ENABLED`（默认 `true`）为 `false` 时 MUST 跳过创建，MUST NOT 删除已存在的指南。启动日志 MUST 记录本次是否创建/补齐（`guide.ensured`），跳过时 MUST 说明原因（`guide.skipped`）。

标题变更 MUST 由迁移（而不是启动逻辑）完成：启动只负责创建缺失内容，MUST NOT 覆盖已存在书籍的标题，避免把管理员的改名改回去。

#### Scenario: 默认开启时创建

- **WHEN** 未设置 `BUILTIN_GUIDE_ENABLED` 的实例首次启动
- **THEN** 启动日志出现 `guide.ensured`
- **AND** 站点里能读到标题为「AI Agent 接入使用指南」的 `ai-agent-guide`

#### Scenario: 关闭后不创建也不删除

- **WHEN** 设置 `BUILTIN_GUIDE_ENABLED=false` 后重启一个已有指南的实例
- **THEN** 不再尝试创建，也不产生重复内容
- **AND** 已存在的指南仍然可访问

#### Scenario: 准备失败不影响服务启动

- **WHEN** 创建指南过程中抛出异常（例如库暂时锁定）
- **THEN** 服务仍然完成启动并对外提供已有内容
- **AND** 错误被记入启动日志

#### Scenario: 启动不撤销管理员的改名

- **WHEN** 管理员把指南标题改成别的名字后重启实例
- **THEN** 启动流程不覆盖这个标题
- **AND** 内容与章节结构保持原样

### Requirement: 迁移前 MUST 自动产出可回退快照

当镜像携带的数据库结构与实际库结构不一致、本次启动会执行迁移时，系统 MUST 在迁移**之前**产出一份一致的数据快照，并存放在持久卷内可预期位置、按配置保留最近若干份。快照 MUST 反映迁移前的已提交数据，MUST NOT 包含未提交事务。快照失败 MUST 只记录告警并继续启动，MUST NOT 阻塞服务。非内嵌文件型数据库（如 Postgres）MUST 明确提示由运维自行备份，且 MUST NOT 假装已完成自动快照。库结构已是最新时 MUST NOT 产生快照文件。

#### Scenario: 有迁移时先快照后迁移

- **WHEN** 用携带新迁移的镜像在既有数据卷上启动容器
- **THEN** 启动日志显示先产出快照、再执行迁移
- **AND** 快照文件位于数据卷的备份目录下，且完整性校验通过

#### Scenario: 无迁移时不产生垃圾文件

- **WHEN** 库结构已是最新时重启或重建容器
- **THEN** 启动日志显示跳过迁移前快照
- **AND** 备份目录中不新增快照文件

#### Scenario: 快照失败不阻塞启动

- **WHEN** 备份目录不可写导致快照失败
- **THEN** 启动日志出现明确告警
- **AND** 迁移与服务启动仍然继续

#### Scenario: 非文件型数据库给出明确提示

- **WHEN** 使用 Postgres 部署且存在待执行迁移
- **THEN** 启动日志提示需要自行用对应工具备份
- **AND** 不声称已产出自动快照

### Requirement: 库结构版本 MUST 可观测

存活探针与就绪探针 MUST 同时返回镜像版本与当前库结构版本。数据库不可达时，库结构版本 MUST 降级为空值，且存活探针 MUST 仍按进程存活返回成功。升级验证 MUST 能仅凭探针响应判断"镜像已更新且迁移已执行"。

#### Scenario: 升级后两个版本都可读

- **WHEN** 升级完成并请求存活探针
- **THEN** 响应同时包含镜像版本与库结构版本
- **AND** 库结构版本等于该镜像自带的迁移头

#### Scenario: 数据库故障不影响存活判断

- **WHEN** 数据库不可达或只读
- **THEN** 存活探针仍返回成功，库结构版本为空
- **AND** 就绪探针返回不可用

### Requirement: 升级 MUST 有默认先备份的一键入口

运维 MUST 能通过随仓库提供的一键脚本完成升级，其顺序 MUST 为「备份 → 保留当前镜像 → 构建/重建 → 等待就绪 → 输出镜像版本与库结构版本」。脚本 MUST 默认执行备份，跳过备份 MUST 需要显式开关。脚本 MUST 在重建前保留当前镜像的可回滚标签，并在失败时输出镜像回滚、数据恢复与日志排查三条命令。

#### Scenario: 一键升级自动备份

- **WHEN** 运维在运行中的实例上执行一键升级
- **THEN** 脚本先产出备份，再重建容器
- **AND** 完成后输出镜像版本与库结构版本

#### Scenario: 升级失败给出回滚路径

- **WHEN** 重建后容器未能达到健康状态
- **THEN** 脚本以非零状态退出
- **AND** 输出可用于回滚镜像、恢复备份与查看日志的命令

#### Scenario: 显式跳过备份

- **WHEN** 运维以跳过备份的开关执行脚本
- **THEN** 脚本打印警告后继续升级
- **AND** 不再额外产出备份
