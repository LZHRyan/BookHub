# Spec Delta

## Purpose

让管理员能在目录里一次完成「调整顺序」与「批量发布/撤回/删除」，而不是逐条点击；每次提交对同一父级是原子的，结果逐条可见，失败项不影响已成功的项。

## ADDED Requirements

### Requirement: 拖拽排序 MUST 限定在同一父级内

管理端目录 MUST 支持在同一列表容器内拖动条目改变顺序：每个分卷的章节表各自可拖，根层的散章表可拖。MUST NOT 通过拖拽改变条目的归属（跨分卷搬动仍走章节表单的「归属分卷」），MUST NOT 通过拖拽调整根层里「分卷」与「散章」之间的相对位置（那仍用上移/下移按钮）。

#### Scenario: 组内拖动章节

- **WHEN** 管理员把某分卷内的第 2 章拖到第 1 位
- **THEN** 该分卷内的顺序随之更新
- **AND** 根层顺序与其它分卷不受影响

#### Scenario: 根层散章内拖动

- **WHEN** 管理员把根层散章表里的第 3 行拖到第 1 行
- **THEN** 这些散章的相对顺序更新
- **AND** 各分卷及其内部顺序不变

### Requirement: 排序提交 MUST 原子且校验完整

一次排序提交 MUST 携带目标父级与完整的有序 id 列表。若提交的 id 集合与该父级当前未删除条目不一致，系统 MUST 拒绝并返回 4xx，MUST NOT 改动任何条目的顺序。

#### Scenario: 缺项或多项被拒绝

- **WHEN** 提交的 id 列表比该父级实际条目少一个（或包含别的分卷的条目）
- **THEN** 系统返回 4xx 并说明排序列表不一致
- **AND** 目录顺序保持提交前的状态

#### Scenario: 提交成功后顺序持久

- **WHEN** 一次合法提交完成
- **THEN** 刷新页面后顺序与提交的一致
- **AND** 该父级的序号被重写为 10/20/30…

### Requirement: 批量操作 MUST 逐条返回结果

管理端 MUST 支持对选中的多个章节执行「发布 / 撤回 / 删除」。服务端 MUST 逐条执行并返回每条的结果与失败原因，MUST NOT 因为某一条失败而回滚已成功的条目。批量删除 MUST 要求显式确认。

#### Scenario: 批量发布部分成功

- **WHEN** 管理员选中 5 个章节执行批量发布，其中 1 个已删除
- **THEN** 4 个变为已发布，1 个返回失败原因
- **AND** 页面提示成功与失败的条数

#### Scenario: 批量删除必须确认

- **WHEN** 批量删除请求未带确认标志
- **THEN** 系统拒绝并说明需要确认
- **AND** 没有任何章节被删除

### Requirement: 批量与拖拽 MUST 记入审计

批量操作 MUST 为每个受影响条目写一条审计（动作与单条操作一致），拖拽排序 MUST 写一条包含新旧顺序的审计，操作者与来源 IP 必须可追溯。

#### Scenario: 拖拽留下审计

- **WHEN** 管理员完成一次根层拖拽
- **THEN** 审计里出现一条排序记录，带父级与新的 id 顺序
