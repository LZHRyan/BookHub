# 检索实现与语义

本文解释「搜什么能命中、为什么」，依据 `app/services/search.py`。看结论可以直接跳第 8 节。

---

## 1. 一句话版本

**中文按相邻两字切成二元组，英文按词小写；写入 SQLite FTS5；查询时同一套切分，用 `AND` 连接多个 token 做近似短语匹配；单个汉字查询退化为 `LIKE '%字%'`。**

---

## 2. 切分：中文二元组

`tokenize()` 逐字符扫描：

1. 遇到 CJK 字符（`U+3400–4DBF`、`U+4E00–9FFF`、`U+F900–FAFF`，外加日文假名 `U+3040–30FF`）就累积到一个"run"；
2. 遇到非 CJK 字符时把 run 冲刷掉：run 长度 1 → token 就是该字；长度 ≥2 → 依次取**所有相邻两字组合**；
3. 最后用 `[A-Za-z0-9_][A-Za-z0-9_+#.\-]*` 抽 ASCII 词并 `lower()`。

以「知识库」为例：

```text
run = 知, 识, 库            （3 个连续汉字）
len(run) = 3 ≥ 2  →  二元组：知识、识库
tokens = ["知识", "识库"]
索引里存的就是 "知识 识库"
```

混排例子「部署 docker」：

```text
tokens = ["部署", "docker"]          # 「部署」长度 2，只切出一个二元组
```

结论：**两字词的 token 就是它自己**，所以「部署」「知识」这类最常见的两字关键词天然能命中；三字及以上会被拆成多个二元组。

索引写入时把 token 用空格拼成一个字符串（`index_text`）存进 FTS5 的 `title` 与 `body` 两列。

---

## 3. 为什么 2 字词能命中，1 字词不行

FTS5 的匹配单位是 token：

- 查「知识」→ token `知识` → 命中「知识库」的 `知识` 这个 token ✅
- 查「识库」→ token `识库` → 同样命中 ✅（二元组的好处：任意相邻两字组合都能查）
- 查「知识库」→ 切成 `知识` + `识库`，用 `AND` 连接 → 两个 token 都在同一章里才算命中（近似短语匹配）✅
- 查单个「库」→ token `库` → 索引里**没有**单字 token（除非它就单独成 run），匹配不上 ❌

所以单字必须走回退分支。

---

## 4. 单字回退：`LIKE`

`needs_like_fallback(query)` 的判定很窄：**整条查询长度为 1 且这个字符是 CJK 字符**。满足时改用：

```sql
WHERE (c.title LIKE '%字%' OR c.content_raw LIKE '%字%')
ORDER BY c.updated_at DESC
```

代价：

| 方面 | FTS5 分支 | LIKE 分支 |
| --- | --- | --- |
| 扫描 | 倒排索引，只碰命中文档 | **全表**（每章原文都要过一遍） |
| 排序 | `ORDER BY f.rank`（BM25 相关度） | `updated_at DESC`（最近更新的在前） |
| 精确度 | 词级匹配 | 子串匹配，「库」会命中「库存」「仓库」「数据库」… |
| 提示 | — | 网页结果卡片显示「单字模糊匹配」徽标（`item.exact`） |

库小、单字查询偶尔用一下没问题；如果你的用法是天天按单字翻，建议换两字以上的词。

---

## 5. 大小写、符号与边界

- **英文大小写不敏感**：索引时 `lower()`，查询时同样 `lower()`，所以 `Docker`/`docker`/`DOCKER` 等价。
- 英文 token 允许的字符：字母、数字、下划线，以及词内的 `+ # . -`（因此 `c++`、`c#`、`node.js`、`main.py` 能整体成为一个词）。
- 查询里重复的 token 会被去重，且**最多只用前 24 个**（超出部分忽略，避免构造超长 MATCH 表达式）。
- 所有 token 都用 `"` 包起来再拼 `AND`，所以用户输入里的 `AND`/`OR`/`NOT`/`*`/`:` 等 FTS 语法符号**不会被当成语法**（防注入、防报错）。
- `LIKE` 分支会把查询词里的 `%` 和 `_` 剔掉（同理防通配注入）。副作用：如果查询词里只剩这些字符（如只搜 `%`），模式会变成 `%%` 命中全部——不要这么搜。
- 查询词总长度上限 **500 字符**（`MAX_QUERY_LENGTH`），超出时网页与 API 都返回 400。

---

## 6. 索引什么时候写、查询过滤什么

这是两层独立的保证，容易搞混。

**写入层**（`index_chapter` / `remove_from_index`）：

| 时机 | 行为 |
| --- | --- |
| 新建章节 | 创建后立即写入（`title` + 渲染后正文抽出的纯文本） |
| 替换内容 / 回滚 | 同一事务内先 `DELETE FROM chapter_fts WHERE rowid=?` 再 `INSERT`，**覆盖写** |
| 软删除章节 | 从索引移除 |
| 恢复章节 | 重新写入 |
| 非 SQLite 方言 | 全部跳过（Postgres 没有 FTS5） |

**注意**：写入层**不看状态**——草稿也会被索引。所以"只搜到已发布内容"不是靠不写索引实现的。

**查询层**（`_base_conditions()`，两个分支都套用）：

```sql
c.status = 'published'       -- 只给已发布
AND c.deleted_at IS NULL     -- 排除已删章节
AND b.deleted_at IS NULL     -- 排除已删 Book
AND b.visibility = 'public'  -- 排除 unlisted Book
[AND c.book_id = :book_id]   -- 可选：按 Book 过滤
```

由此：

- 草稿、已删除、`unlisted` Book 下的章节**永远不会出现在搜索结果里**；
- 撤回一个已发布章节后，它立刻从搜索结果消失（状态字段变了，索引留着也无害）；
- 内容改完立刻生效（覆盖写和正文更新在同一个事务里提交）。

## 7. 片段（snippet）怎么来

`make_snippet()`：

1. 把渲染后的 HTML 抽成纯文本、空白压缩；
2. 候选命中词 = 整条查询 + 各 token，按长度倒序；
3. 找**最早出现**的那个命中位置（不区分大小写）；
4. 取命中位置前后各 `SNIPPET_RADIUS = 90` 字符，两端不足时不加省略号、超出的加 `…`；
5. 先 HTML 转义，再把所有命中词包进 `<mark>`，并合并相邻/嵌套的 `<mark>`；
6. 完全没命中（LIKE 分支可能只命中标题）→ 返回开头 180 字符。

片段里的 `<mark>` 是页面唯一允许的"富文本"，其余一律转义，所以正文里写 `<script>` 不会在搜索结果页执行。

## 8. 已知限制（都是有意取舍）

| 限制 | 影响 | 备注 |
| --- | --- | --- |
| 只能按相关度排 | FTS 分支固定 `ORDER BY f.rank`，API 没有排序参数 | LIKE 分支反而按时间倒序 |
| 不做同义词 / 近义词 | 搜「部署」不会命中「上线」 | 文档标题写全关键词 |
| 不做拼音 / 首字母 | 搜 `bushu` 找不到「部署」 | 中文只能搜汉字 |
| 不做停用词、不做词典分词 | 「的」「了」也会被当二元组的一部分 | 对短查询影响不大 |
| 单字精确度低 | 见第 4 节 | 页面有徽标提示 |
| 最多 24 个 token | 超长查询后半段被忽略 | 实际使用中不会碰到 |
| Postgres 下无 FTS5 | 所有查询退化为 `ILIKE` 全表扫描 + 时间排序 | 见 [deploy.md](deploy.md) 第 8 节 |
| 索引不含版本历史 | 只能搜到**当前**内容 | 想搜历史版本请到版本页看原文 |
| `reindex_all()` 没有命令入口 | 想整库重建索引要自己写脚本调 `app.services.search.reindex_all(session)` | 一般不需要：写入路径已保证一致 |

## 9. 排障

| 现象 | 排查方向 |
| --- | --- |
| 明明有这个内容却搜不到 | 章节是否已发布？Book 是否 `unlisted` 或被删？是否只搜了单个汉字？ |
| 搜索结果顺序很怪 | FTS 分支按 BM25 相关度（`rank` 小的在前），不是按时间 |
| 单字搜索特别慢 | 走 `LIKE` 全表扫描，属预期；数据量大时避免单字查询 |
| 索引和内容不一致 | 检查是不是有人直接改过数据库；正常路径（创建/替换/删除/恢复）都在同一事务里维护索引 |
| 切到 Postgres 后搜索变慢 | 预期：没有 FTS5，全靠 `ILIKE` |
